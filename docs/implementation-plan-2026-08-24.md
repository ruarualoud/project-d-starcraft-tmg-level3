# StarCraft TMG Level-3 implementation plan

Date: 2026-08-24
Status: active long-task implementation plan
Wayfinder: [StarCraft TMG Level-3 Platform Wayfinder](../../.scratch/starcraft-tmg-level3-platform/map.md)

Fixed development root: `starcraft-tmg-level3/`. All new product code, contracts, verifiers and generated evidence stay below this directory. Repository-root StarCraft implementations are read-only Adapter inputs until an explicit integration gate authorizes a bounded change.

## Product outcome

Evolve the existing StarCraft TMG product and Battle Lab into one Level-3 platform whose Web and App clients share authoritative game contracts, official-source data and translations, room/replay state, direct-Provider role Agents, DSH-backed offline Skill generation, and player-view MuZero-compatible evidence.

The current UI is an experience asset, not a state authority. Rules, Referee, Agent/Skill, and Learning claims remain separate.

## Fixed decisions

- Recover the Expo product source and keep Battle Lab as the developer/referee/Agent-observability surface; both consume one domain SDK and service protocol.
- M1 has two mandatory lanes: an authoritative cross-client movement atom and a real room-connected Kerrigan Adjutant demo.
- Official StarCraft TMG sources own canonical game facts. Machine translations are provenance-bearing display sidecars.
- Kerrigan is the default product Adjutant role, not a canon Adjutant title. The first proposed edition is the rights-gated post-Zerus/pre-Legacy Primal Queen.
- Tutor, Opponent, Commentator, and Companion use isolated sessions, tools, memories, and visibility. Only the Opponent decision channel may submit a LegalSpace candidate.
- Online Agents use direct Providers with administrator profiles and session-memory-only BYOK. DSH is used only for offline Skill candidate generation.
- The first MuZero phase exports and validates data but does not train a learner or grant training truth.

## Authority planes

1. **Source plane**: raw official snapshots, source registry, hashes, diffs, normalized data, translation sidecars.
2. **Rules plane**: normalized state, LegalSpace, deterministic transition semantics, rule-source diagnostics.
3. **Referee plane**: revision/CAS, preview/apply parity, room capabilities, append-only receipts, public/private journal projections, replay.
4. **Agent and Skill plane**: CharacterPackage/worldbooks, direct Provider sessions, role tools/memory, offline DSH candidate generation, evaluation and promotion.
5. **Learning plane**: player-view observations, action encoding, episode lineage, leakage tests, round-trip export and independent eligibility.

### M1 — Dual vertical slice

Execution lane:

- LegalSpace exposes the complete union of exact finite actions and parameter domains; movement is a rules-owned path domain and search suggestions remain non-authoritative.
- Preview binds the signed MatchBinding, room/state revision, state and LegalSpace hashes, canonical proposal, explicit GameClock, events, confirmation policy, optional ChanceTicket commitment, and post-state hash with an HMAC seal.
- Apply requires the same sealed preview, expected revisions, server-owned SeatGrant, current fenced ControlLease, idempotency identity, and any required human confirmation, then appends an Ed25519-signed receipt.
- A replay resolves the exact frozen dependency set and reproduces the same signed receipt/state chain or enters explicit quarantine; it never substitutes current rules.
- Web and App consume the same service contract.

Adjutant lane:

- A versioned Kerrigan CharacterPackage and worldbook are loaded through a direct Provider session.
- The Adjutant reads the same room projection and LegalSpace used by the client.

- The trace records prompt route, tools, rule/Skill refs, memory refs, versions, decision alternatives, confirmation, result, and training ineligibility.

## First implementation increment

The first increment is being upgraded from the prototype in-memory slice to an authoritative engine, a durable `RoomStore`/room runtime, and a transport-neutral HTTP Adapter. The deep mutation interface is:

```text
createEnvelope → legalSpace → preview → apply → replay
```

Its implementation owns RFC 8785 canonicalization, SHA-256 identities, Ed25519 permanent signatures, HMAC short-lived seals, proposal identity, complete hybrid LegalSpace, fixed-point arbitrary-path validation, revision/fencing checks, confirmation policy, deterministic rules time/chance, receipt construction, three-ledger projection, journal chaining, dependency freeze, historical rules display and exact replay. Callers may instantiate only a rules-owned parameter domain; they cannot supply role, side, current state, rules version, authority, or a new arbitrary mutation type.

The root legacy `apply-action` route remains untouched but is restricted to an isolated development sandbox. It cannot create Level-3 receipts, enter Level-3 rooms, or produce training evidence. New clients, rooms and Agents target `/starcraft-tmg-level3/api/v1/rooms/*`; this Adapter delegates every state mutation to the deep authority interface. Root legacy integration happens only after Expo/Battle Lab migration and parity evidence define an explicit boundary.

## Exactness and promotion policy

- Unsupported rules fail closed or remain explicitly display-only; source text is not silently converted into executable truth.
- A successful preview, apply, replay, Provider response, DSH run, or export does not grant rule truth, Skill promotion, or training truth.
- Roleplay/worldbooks, machine translation, user memory, strategy Skills and community material cannot overwrite official rules facts.
- Every accepted state change is revision-bound and receipt-bound. Every replay claim must reproduce the same semantic receipt chain.
