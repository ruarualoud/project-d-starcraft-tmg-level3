# T27 / S272 P2：证据目录重复扫描定点优化

## 实际问题

同 Run 47927 接受工作单后持续高 CPU，非 Provider 断连。对实际进程做了一次 CPU 调用栈采样：有效窗口 10,188.933ms / 3898 样本，其中 2505 个落在 `inspect → clone → structuredClone`，485 个为垃圾回收，374＋282 个落在 `inspect → directory` 的扫描函数，另有目录对象复制。采样只定位当前区间，不能外推整个生成流程。

已确认代码对每条 evidence 都 `state.reads.filter(...)`，当前规模约1368证据、2783条读取记录，一次目录访问约380万次比较。这里没有模型判断，只是重复机械扫描。

## 只修确定的重复扫描

`roster-decision-workflow-v1.mjs` 内部 `directory(consumer)` 先扫描一次读取记录，为该 consumer 建立 evidence→readPaths 索引，再按原证据顺序生成目录。

- 不缓存跨请求状态；新读取和新scope立即生效。
- 路径顺序、重复路径、current/historical、missing/unsupported、read/partially_read 判定保留。
- 每条返回仍是独立副本，不向调用方暴露可修改的内部数组。
- 不删历史、不减少prompt内容、不改模型/策略/费用/生命周期，不改变公开接口。
- 大状态 `structuredClone` 热点尚未改，不声称全部本机耗时已解决。

`scripts/verify-slice272-evidence-directory-scan-v840.mjs` 使用当前真实证据/读取记录，在隔离只读工作流接缝检验；不恢复或执行付费工作。
