# Skill 生产内检、上下文与升级链路：一手资料对照

日期：2026-09-06。范围：StarCraft TMG；不刷新官方游戏数据。
本报告是代码审计和方案建议，不是五件套完成或真实复盘验收。
按用户要求不使用 Codex 子 agent；research 技能建议的后台委派不执行。

## 结论

查到的是可组合的工程模式，而不是一个装上即可保证没有幻觉的统一标准。
本项目应采用：完整来源上下文、外部可执行反馈、结构化问题单、有界局部
修订、验证器校准、跨模块回归、持久化恢复，以及独立的发布/回滚门。
DSH 是执行这些步骤的离线 Harness，不是事实验证器。

## 一手参考与适用边界

1. **Evaluator–optimizer**：生成、评价、依据反馈修订；适合有明确评价标准的任务。
   同文强调从实际环境/工具获得反馈并设置停止条件。可作为生产控制流参考，
   不是正确性保证。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
2. **CRITIC**：把外部工具查询与验证纳入批评/纠错循环。我们对应的外部反馈是
   冻结官方原文、Rules 内核、真实 Room/Replay，而非让模型凭印象再打分。
   论文没有证明所有任务可无幻觉。[CRITIC](https://arxiv.org/abs/2305.11738)
3. **纯自纠错的限制**：ICLR 2024 的研究指出，在其推理实验中，无外部反馈的
   自纠错可能不能改进，甚至退步。这是特定研究的结果，不是“所有新模型永远
   无法自纠错”的定理。[Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)
4. **上下文检索**：脱离全文的分块会失去主体、时间与条件；应保留块在全文中的
   定位。对足够小的知识库，全文上下文也是明确提出的方案。检索增强与自动摘要
   本身仍需评估，不能把摘要升级为规则来源。
   [Anthropic：Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)
5. **上下文工程**：长上下文也会有注意力与压缩损失，需要结构化记录和相关性
   管理，而非无上限堆入历史。对本项目，固定规则背景与当前问题/证据应分区。
   [Anthropic：Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
6. **混合评价与回归**：程序、模型和人工评价各有边界；程序判定也会过度僵硬，
   模型 Judge 需要校准。能力评估与防退化回归要分账。
   [Anthropic：Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
7. **GEPA**：根据运行轨迹、失败信息与指标定位模块，提出修改并在验证集比较，
   而非只保存最高一次分数。可借鉴于 Prompt/SkillOpt，但其原生优化对象主要是
  程序/提示，本项目 Skill 版本、Rules 权限和发布需要自己的 Adapter。
   [DSPy：GEPA](https://dspy.ai/api/optimizers/GEPA/overview/)
8. **Reflexion**：利用反馈和情节记忆改善后续尝试，可启发赛后反思；反思文字
   不是已证明有效的策略，不能直接写入正式 Skill。
   [Reflexion](https://arxiv.org/abs/2303.11366)
9. **持久化工作流**：LangGraph 区分会话检查点和跨会话 Store，并提供失败恢复
   的基础设施。它解决持续执行，不替代领域正确性和 Provider 费用结算。
   [LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## 真实失败的诊断，不统称“模型幻觉”

| 已观察问题 | 归因 | 应做的修复 |
| --- | --- | --- |
| 审核额外附带准确的段落引用被拒 | 输出合同过严 | 精确允许并验证该字段，不能忽略任意未知字段；已修 |
| 设计说明没有被改写成规则，机械覆盖失败 | 覆盖定义不当 | 独立记录“规范性规则/非规范说明”，不能强造规则凑数量 |
| 正文完整但少引用一个相邻段落 | 引用覆盖/补丁能力不足 | 允许保留正文的有界引用补丁，随后重验来源与语义 |
| Generator 没执行 read | 输入合同与工具遵循问题 | 主机直接提供必需原文；分别记录 prompt 暴露与真实 tool read |
| Editor 返回空补丁 | 没有取得进展或有审查争议 | 记问题单、扩上下文/核查审查依据；不当作 JSON 失败重试 |
| 整个主题过长，评价前预算拒绝 | 上下文预算设计问题 | 评估完整输入管线容量并按依赖组织，不删除关键背景凑门禁 |

## 上下文：建议先全局读、局部写、整体查

本地冻结原文实测（不是 Token 数）：Core 220 行 / 169,680 字符，FAQ 68 行 /
15,326 字符，总计 **185,006 字符 / 186,485 UTF-8 bytes**；另有 83 个官方产品
数据行 / 91,012 字符。当前每批携带完整 FAQ，却没有完整 Core 或已校验的全局
规则背景；完整来源阅读分母不能证明跨章上下文已交给每次生成。

Provider Profile 配置的 `contextBudget` 为 1,000,000，但 `model.mjs` 还有
180,000-byte 的保守输入门。这个配置不证明实际 Token 数或服务商支持。
必须测量完整请求、重试上下文、DSH relay、IPC、请求字节、超时、费用上界，
才能调整容量，不能只改一个数字或关闭保护。

推荐先比较两个冻结方案，并按遗漏、矛盾、成本和耗时选择：

- **全文背景方案**：稳定的完整 Core+FAQ 为来源前缀；当前章节、相关产品数据、
  全文目录/词表、问题单和允许修改的范围是工作区。按批生成不代表只看该批。
  缓存是否命中以真实 usage 为准，不预先承诺价格优势。
- **依赖上下文方案**：若全文方案实测不合适，保留全局规则结构和来源索引，
  为当前条款补父章节、邻接段落、术语定义、所涉状态/阶段/例外及 FAQ 覆盖链。
  缺依赖则扩展原文，不单靠 Top-K 检索或反复摘要；摘要仅导航。

两者都必须做合并后的跨章检查。声明与规则原子图建立精确映射后，修改一个
条件要使相关章节、种族和正反对抗依赖失效并重验，而不是只看当前小段。

## 内检应成为可追踪的问题解决循环

每个问题单至少持久化：问题 ID、候选/上下文/来源 hash、受影响声明、失败类型、
原文或 Rules 反例、建议修复路径、已试补丁、关联依赖和当前处置。

`候选 → 分类验证 → 问题单 → 补证据/局部修订/核查审查器 → 受影响回归 → 整体验收`

重要边界：

- 格式修复不能偷偷改结论；引用修复和语义修复分开。
- Reviewer 的否定也要有具体来源/反例，不能因为“再加一条更完整”无限加料。
- 非规范性说明只能在证据充分的独立处置下豁免“必须生成规则”，不能靠把状态
  名字改成 `covered` 或让生成者自签豁免。
- 连续相同错误、空补丁或无进展触发分类升级/有限隔离，不重新抽样直到侥幸通过。
- 发现验证器有误，先用独立回归证明，再产生验证器新版本；保留原失败，禁止
  为当前候选临时放宽验收门。
- 开发反例可反馈给修订器；真正 held-out 不反馈答案。用于修复过的题转为回归，
  不再冒充新的独立泛化证据；保留首轮与修复后分数。
- Rules 程序反例优先于 LLM 投票，但测试与内核也须来源校验；用同一段代码
  算预期再证明自己正确，不是独立验证。不可执行的策略必须标为假设。
- 稳定性指可重复观察、可恢复、受控收敛或明确失败，不保证所有任务都会成功。

## 赛后与 SkillOpt：同一验证体系，不是另起聊天

真实 Match/Replay → 验证日志/视角/版本 → 区分规则、检索、工具、策略和随机结果
→ 使用决策前信息提出策略假设 → 同条件可执行对照与反例 → 版本化小补丁
→ 历史回归 + 未参与优化的对局/题集 → 晋级候选 → 明确发布与回滚。

输了一局不自动证明策略错，反思一段文字也不算策略提升。没有可证改进时，
`completed_no_skill_change` 应当是合法结果。训练真值、规则修改与线上发布继续
各自关门；不把本报告、模型共识或模拟用例提升为真实对战效果。
