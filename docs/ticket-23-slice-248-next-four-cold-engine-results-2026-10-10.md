## 为什么看起来更慢

1. **已确认测量起点不一致。** 上一轮在准备时调用 `authorityEngine.replay`，顺便建立引擎私有的已核验历史前缀 memo。这次直接读保存的签名 envelope，没有建立该 memo；首次行动 Replay 因此重新执行历史。A 的准备恢复由 65.074s 降至 0.372s，但行动 Replay 由 8.904s 升至 98.635s。B 的准备恢复 11.034s → 0.313s，Replay 9.219s → 51.452s。额外历史工作不是 owned 日志读取本身。不能把这些总数作为持续房间的受控 A/B，亦不能减去这一段后假称测得“暖房总时间”。
2. **不只模型工作量。** A 新旧都是五轮，模型 74.880s → 72.308s，总时间仍增加，不能归咎于模型多查资料。B 四轮 → 三轮，模型 95.842s → 73.483s，但新旧目标/查询组合不同；旧 90.956s 概率 worker 与此次 32.217s worker 的目标不同，禁止宣称同请求提速。
3. **还有真实慢点未解释完，但旧“同请求”比较已撤回。** 原报告误从模型 `query_requests` 筛出队形请求：队形由 Host 根据 Planner 结果生成，两边筛选结果都是空列表，不能据此证明请求相同。实际旧请求指向 marker 2，新请求指向 marker 4，目标、锚点及权重不同；110.025s 与 239.871s 不构成同请求代码 A/B。它们仍与额外冷 Host Replay 重叠；CPU 入场仅毫秒，不能将所有延迟归因排队。Host 的 Preview/Apply/Replay 和队形父准备尚未全部纳入同一 CPU 预算，争用未被定量分摊。

## “恢复”与真实产品的区别

本观察的恢复是重新建立历史动作 7/106/113 的隔离实验输入，用来比较原场景。它不等于玩家新开局的流程。

- 新房间：创建初始军表、地图、状态，没有旧对局历史可恢复。
- 持续房间：状态及引擎保留；每次行动核验完整结果，可以复用已核验历史。
- 断线/进程重启后续局：加载持久化状态，必要时做一次历史恢复/核验。这是恢复已有对局，不应成为每个正常行动的固定环节。

计时来源已修正：真实模型观察脚本不再用保存 Envelope 跳过原生历史 Replay，而是在 setup 中完成原生恢复；保存件仅用于完整结果比对。正常行动仍含本次 Preview、Apply、Replay 与记忆保存。语法检查已过，修正后的暖态完整行动时间尚未实测，不能直接扣旧历史时间得出。
