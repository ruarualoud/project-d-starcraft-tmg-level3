# 06 — 验证、自动恢复与准出规范

沿用工程先行和实现纪律，不另设无限审核。手册中的验证项是交付要求；只有实际结果文件及后继才能标通过。所有示例均指隔离候选，不允许修改原房来造测试场景。

## 1. 开始改动前：原因、方案、影响、无损证明

在唯一验收卡填写四项，随后实现：

1. 原因：来源变了、合同遗漏、错误接线、算法错误、保存/恢复错误，还是模型做了合理但差的选择。写出真实输入和期望，不凭截图推断规则错。
2. 方案：明确生产者/消费者与状态所有者；改变的数据结构和后继。先找到复用处，避免在UI、Planner或实验脚本各补一个特判。
3. 影响：逐入口列新旧发布、编军、房间、工具worker、Plan首次/修订/纠错、在线决策、保存回复消费、冷恢复、客户端。无影响也写出依赖依据，不靠“应该没事”。
4. 无损证明：旧房/旧发布选哪个最小基线，预期哪些字节或语义不变；新版哪些行为应变。只跑与改动直接相关的门。

遇到具体Bug先用真实工厂和输入复现失败。新功能按用户交付建立具名场景；禁止新增仅镜像实现、只检查函数存在或为测试方便绕开产品入口的测试。模型请求不能替代工程验证。

## 2. 验证层次与独立预期

| 层 | 证明什么 | 不证明什么 |
|---|---|---|
| 来源/静态合同 | 原件、版本、覆盖登记、Schema与实际参数一致 | 动作能执行 |
| 原子行为 | 在明确前置下得到官方规则要求的后态/拒绝 | 产品已选到它 |
| Room/Query同路径 | 目录→合法参数→预览→执行→事件/后态，查询和执行口径一致 | LLM会选择好策略 |
| 外层产品交接 | 用户入口/正式调度消费结果并自动进入合法后继，保存回复可续消费 | 真实Provider一定稳定 |
| 真实产出 | 真请求生成合法表/Plan或执行动作，成本和原件可追踪 | 策略胜率更高 |
| 独立比较 | 受控场景下结果/选择改变及其统计局限 | 全局、跨版本通用最优 |

预期必须来自冻结条款与独立计算/人工可读事实，不拿被测函数的输出当自己的正确答案。随机攻击核骰池、概率、选择、采样参数与回执重放；不可要求一次实际伤亡等于数学期望。

## 3. 最小原子接线验证矩阵

每条定义登记类型及证据。复用原子的定义只需新增参数绑定正确性＋必要组合边界；算法未变且输入合同一致时引用原有证明。独特时序必须新增具名产品证据。

| 类型 | 最小成功路径 | 必要反例/边界 |
|---|---|---|
| 数值/编军参数 | 官方源→菜单与审计→保存→恢复同值 | 旧价/错势力/超预算不可借新旧混用通过 |
| 主动动作 | 在对应phase进入legalSpace→选择语义→Host实例化→preview→apply→下一activation | 错阶段/缺资源/无资格/过期revision；拒绝不扣费 |
| 反应 | 原动作事件打开窗口→正确席位选择→结算一次→原流程继续 | 不满足trigger不出现；重复投递不重复扣费/结算 |
| 被动/修改器 | 触发源进入kernel，查询与执行同时体现并能指出来源 | 失效范围/目标/来源移除后不残留 |
| 延迟/token | 生成→保存→冷恢复→目标时间触发→清理 | 提前不触发；处理后再次恢复不重复触发 |
| 状态替换/模式 | 同一身份切换，保留规则要求保留的数据并更新新能力 | 不重复占名额/扣费/恢复被消耗资源 |
| 任务/部署 | 对应规模/部署阶段→合法区域→计分生命周期→胜负 | 第1回合禁计分、竞争点、失去Supply等依实际任务条款 |
| 几何 | 全底座合法路线/终点/地形行为→同位置投影 | 中心合法但边缘出界、窄道、重叠、飞越后落点非法 |

拒绝用明确ruleCode/事实，不能把模型换一种说法后的不合法动作自动执行。模型选错策略不构成工程阻塞；模型引用错误事实则返原生事实并允许它重新选。

## 4. 工具完整合同与对照判定

每个工具变更至少登记：工具名与版本、用户语义参数、Host绑定字段、输入快照、输出判定类型、适用条件、不会回答的问题、缓存键、错误分类、所有消费者。

Host负责releaseId、room/revision、候选/地图/任务引用、nonce/签名/回执关联、数据摘要；模型选择单位/目标/动作/模式及实验条件。仍需检查语义值合法，不能把未知名称静默映射成任意对象。

对照规则：

- 同release、同state、同动作候选：查询声称“本候选合法”时，preview必须一致；期间房间变化应返回stale并刷新，不算前次查询错误。
- 路线存在/静态队形/条件可达：只与其所承诺的范围对照，不能强迫它证明真实行动或全场可达。有限搜索失败输出exhausted/unknown及搜索域，不输出全域无解。
- 当前占点：用原生任务控制kernel，同步阵营竞争、底盘、Supply、资格；“距离范围内”不能转写为“可控制/会得分”。
- 预计伤亡：同武器、目标、护甲、技能、卡、距离、高差和移除策略；明确单包/连批范围。种子采样重放核行为，分布比较核统计，不把两者混为一谈。
- 新单位、新能力不存在于工具菜单：这是覆盖缺口；不得将不存在的值转成普通移动/普通枪来生成看似成功的证据。

统一端口必须覆盖写表实验、固定表Plan、Teach作者/调查/审核、实战Planner/Action、计划更新、Web计算器、复盘实验。每个消费入口的完整大对局无需重跑，但其实际构造器选择到同release和工具contract的交接必须有证据。

## 5. 产品边界单步验证与故障注入

复用 scripts/lib/product-boundary-check.mjs 的 runProductBoundaryCheck。它支持具名read→compile→consume→successor→coldRecovery边界、证据和检查点。identity由真实factoryModule、factoryExport、sourceRef、contractVersion构成，不能为跳过旧失败而换身份。先读实际helper和产品接口，别从文档猜可执行参数。

下面是设计顺序，**不是可以直接运行的代码**：

    realProduct = 用正式工厂打开隔离来源/存储
    request = 从外层产品入口形成待处理操作
    savedReply = 注入符合当前Schema的语义回复（只替换Provider传输）
    consume = 由正式消费入口处理savedReply
    successor = 由正式调度推进，读取真实下一步/后态
    closeAndReopen = 关闭实例后从同一持久化数据恢复
    verify = 核对已提交效果/后继/调用数，不能再次购买或提交

先用Schema/原生菜单构造夹具，严格区分Provider实际看到的字段和Host持有的内部字段。模拟回执不能用于对外宣称原生成功；注入只替换外部回复，不替换Rules/编译器/调度器。

必要异常按改动面挑选，不能每片全部重跑：

| 故障 | 产品应如何处理 | 核验重点 |
|---|---|---|
| 源文件缺失/版本错 | 拒绝当前候选并列精确缺件 | 不换旧数据、不污染原发布 |
| 仅多余格式字段/可确定包装错误 | Host按明确Schema做无损投影或包装 | 不丢语义、不让模型重写签名 |
| 缺必需语义/未知目标 | 给已核事实与最小纠错问题 | 不编造目标/默认动作 |
| 正常回复已保存、消费前退出 | 消费原回复并继续一次 | 无第二次Provider调用 |
| Apply已提交、后继未保存 | 从原生事件/状态重新确认，再派发未完成后继 | 不重复扣费、损伤、计分 |
| 房间在查询期间变化 | 返回stale，重取相同语义的新快照 | 不把旧候选当合法新动作 |
| worker迟到或旧release缓存 | 结果身份比对、拒收过期值 | 前台不会得到另一房的事实 |
| 传输未完成且无可消费回复 | 记录transport状态/未知费用，按既有策略有界退避 | 不手写成功，不无限立即重试 |
| 磁盘不足/存储写失败 | 在不可提交边界安全停止，保存最小错误 | 不返回成功；不自动删除原件 |
| 同query无新事实反复提出 | 复用证据/告知已答与作用域，转回决策 | 不自动选pass，不无限查证 |

测试中确实失败才能开相应修复项。使用同一命令且没有新改动不重跑；有改动也只跑一次对应门。达到会话三轮停止边界时报告具体生产/夹具原因；仅沿已经授权的定点补验处理，不换名字绕过。通过项的代码或依赖未变时引用证据，不重复证明。

## 6. 如何记录一条可复用的通过证据

每个结果需包含：被验证release和契约版本、生产工厂、实际入口、来源路径/不可变身份、注入范围、前态、操作语义、实际结果、后继、冷恢复结果、失败分类及覆盖边界。原始模型正文/收费记录引用原件，不复制进每个workflow。

证据应能回答：

1. 页面/模型能不能发现并选择？
2. Host实际填了哪些参数，填值来源是什么？
3. 哪个规则模块做判定，采用哪个版本？
4. Query与Apply怎样对照，哪些是概率或条件结论？
5. 保存后下一个真实产品步骤是什么？
6. 退出再打开会不会重复执行/计费/丢结果？

代码扫描发现同一import只证明共用代码，不等于实例读取同一数据。必须读取实际产品构造出来的release/参数事实及后态。测试摘要为passed但没有这些字段，不能宣称接线完成。

## 7. 状态、磁盘、Git和权限

- 每项用一张验收卡＋implementation-plan.json状态；build仅放本项最小输出。不要复制完整历史build、几十份room.sqlite或整个workflow作为夹具。
- 隔离方式优先不可变原件引用＋有界overlay/由实际工厂重建的最小状态；涉及真实SQLite一致性时沿已有snapshot方式，不能复制正在写入的数据库主文件冒充完整快照。
- 模型原件、费用、真对局和有效经验保留。任何自动清理/删除/无损压缩后删原件都需要当时授权；本方案没有新清理命令。
- 计划文档更新只做链接、路径、JSON依赖与状态一致性检查，不运行产品测试。
- 修改前后读当前相关Git差异，保留其他任务改动；只在用户要求时提交/推送，按子项提交必要文件，不用git add .。不切分支、不重置、不改旧回执，不把缓存/密钥加入Git。
- 不安装、不擅开服务/付费调用；遵从当前授权。权限已经授权则继续，不因本手册多造确认；真实付款暂停有效时先完成不依赖付款的工作。

## 8. 最终准出分四列

| 实现 | 产品接线 | 真实产出 | 策略效果 |
|---|---|---|---|
| 代码/数据有没有 | 正式入口是否执行且可恢复 | 是否实际生产/对战成功 | 是否受控对比优于基线 |

工程错误与事实错可以阻止对应路径发布；合理策略分歧、未证明更优不能变成无限审核。整体16项完成率来自已交付子项，临时测试数、报告页数、新增原子登记数都不能增加该完成率。
