## 目标

新增数据能通过同一产品链路完成：人工写表／AI从头写表／固定表写Plan → 创建房间 → 人人／人机／机机 → 计分终局 → 恢复与回放。已有旧版本房间、战报、暂停复盘保留原规则，不原地迁移。

当前确认增量：19条单位记录、8战术卡、4势力、162产品效果定义、4任务记录、3部署卡，以及旧卡调价和FAQ v1.3。162不是新增原子数。FAQ精确原子差分由04交付，定义复用比例由各能力纵切证明。

## 执行顺序和完成判定

### 当前 Wave3 续行规范

1. 先完成组件。每轮至少准出一条未过组件，通过原生消费、后继与相关冷恢复后才能增加已验数。已有通过证据直接复用；当前组件数以实施清单为准，达到 162/162 后推进正式 Match。
2. 正式 Match 每条接线有具名编号、验收出口、状态和证据。进入此阶段后每轮至少推进一条到新的产品验收节点，达到该项出口才增加准出数。涉及军表的接线同时列稳定定义 ID 和实测军表范围。
3. 汇报分别给组件完成数、正式 Match 子项完成数和 Ticket 28 总计。遇到明确缺件或达到已有重试边界，登记具体阻塞并继续同阶段独立项。 [实施清单](../../../coordination/wave3/implementation-plan.json)


默认01→02→03→04→05→06→07→08→09→10→11→12→13→14→15→16。依赖以实施清单为准：14真实生产受额度暂停限制时，继续15的工程部分和16的离线子集，明确保留真实验收未完成。06～12在各自纵切中接工具和UI，12/15负责汇总缺口，不是把接线拖到最后。

每项顺序一致：

1. 在一张验收卡确定本项事实／新增功能、受影响入口和期望，不先开模型试错。
2. 追到生产函数、读取／写入所有者、存储和后继；填写实际路径，不用“共享模块”代替。
3. 取真实冻结材料或实际工厂生成的隔离状态。已有具体Bug先保存失败；新功能以具名验收场景建立行为目标。
4. 成组修改所有受影响消费者；模型语义与Host包装分开。构建候选版本，旧发布不动。
5. 对本项运行一次相关产品边界验收，保存成功断点；仅新代码实际影响的门补验。失败按产品／夹具／外部／模型语义分类。
6. 工程边界通过且付费暂停已解除，才做真实调用；保存原回复、公开理由、工具证据和成本。
7. 报实现、接线、真实产出、策略效果四层状态；更新本项状态与短TASKS，不用报告数量增加完成率。

既有已过门不重跑；三轮收敛和已授权定点补验按会话规则执行。用户要求的新增功能验收可以补定点场景，不创建与行为无关或仅复述实现的单测。

## 最先需要处理的风险

- 写表产品 createRosterPlanningProductModuleV1 直接使用旧source-lock fixture。先接发布上下文，否则新表可能仍用旧价格／资格。
- 多个执行器硬绑定旧数据hash；能力IR用整条记录hash和数组序号生成ID。02处理身份和兼容映射，不全局改常量／删校验。
- transition-v1.mjs的相对Rules导入，经符号链接实际指向主仓库 scripts/starcraft-tmg-rules-v0.mjs。它是共享只读依赖。优先通过现有 options.rulesRuntime 注入新运行时；不要在旧共享脚本上覆盖Wave3数据。
- 公共API规则节未变不代表FAQ没变；PDF修订色彩／删除线不能从抽取文字猜。
- 可查询“距离”不证明控制点，静态摆放不证明可移动到达，概率不等于实际骰子结果。工具更新须保持这些边界。

## 工作范围和验收范围

当前代码检查只证明入口和缺口存在，没有做Wave3产品准出。01的候选来源不直接成为生产真值。414条产品定义需要完整用途归属，但证据按“定义绑定＋共用原子组合＋真正独特分支”复用；不要求414场对局，也不把保留展示的旧原子强行执行化。

完整W3发布前必须关闭所有范围内Critical/High事实或工程缺口；合理次优策略、未测收益、Medium发现按原规则记录。默认发布、Git提交／推送、清理及安装服从当时用户授权，手册不新增审批轮次，也不授予后台自动续跑。
