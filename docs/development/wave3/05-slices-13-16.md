## T28-W3-13：建立可持久化的增量失效与更新计划

依赖02、12。目标：只更新受影响的事实与策略，不重写全部Skill，也不让旧经验带着新规则身份投入生产。

现有入口：packages/strategy-skills/incremental-skill-freshness-runtime-v1.mjs；sqlite-strategy-release-store-v1.mjs、postgres-strategy-release-store-v1.mjs及对应合同；online-strategy-skill-registry-v1.mjs。现有freshness运行时使用内存Map，已有算法不能直接视为持久化产品接线已完成。

步骤：

1. 建立规则/单位/卡/任务/几何→Skill章节/条件经验/Plan事实依赖索引。每个依赖包含语义ID、依赖类型、适用版本、用途及原证据引用。价格事实和策略建议分开。
2. 用01/04的语义差分生成刷新计划：事实字段变化→重算工程事实；行为变化→失效相关案例与推论；纯文案/时间戳→不强制重新生产；新内容→补对应覆盖，不默认全量重写。
3. 旧Skill缺少细粒度依赖时，标“待建立依赖”；先确定关联章节范围，再验证适用性。不能把缺索引解释为不受影响，也不要无条件重做所有包。
4. 对经验使用四类适用性：可直接沿用、在新版本复核后沿用、等待新证据、与新规则冲突。保留原版本内容和结论；新适用性判定是另一个记录。未定假设可检索，但不能被当作已证明事实。
5. 将刷新计划、处理进度、候选版本、选中指针及回滚记录接入现有存储合同。用相同端口服务本地SQLite和已有PostgreSQL adapter；不在本任务擅自迁移生产数据库。
6. 正式产品在创建新Plan/新房间时解析同一release的Skill组合。旧房间固定原组合；恢复不从“最新”指针重新选包。发布选择必须先完成适用性检查，不以散落hash绑定让无关旧包失效。

验收：一个调价只影响编军事实及依赖预算的章节；一个新墙体行为影响对应空间经验；一个纯大小写变动不触发整包生产；断电/重开后计划和选择一致；旧房间读取原包；新房缺适用包时明确显示能力缺口。真实SQL adapter若无可用环境，记录未验收，不能用内存替代通过。

交付：持久化依赖图与刷新清单、产品消费入口、选择/回滚/恢复证据、精确待更新Skill章节表。此项不需要付费生成。

## T28-W3-14：按影响增量生成策略包

依赖03、07～13。必须在额度恢复且用户允许真实生产后执行；先完成编译和消费的离线交接。

### 范围

本地现有11包：总规则1、势力4（Terran Armed Forces、Zerg Swarm、Kerrigan Swarm、Daelaam）、有向对抗6（Terran Armed Forces与其余3势力双向）。这不是10势力完整覆盖。

本期基础目标为总规则1＋势力10＋现有有向对抗6＝17包：复核/增量更新现有11，新增6势力包（本次新增4势力，以及已有却未覆盖的Raynor Raiders、Khalai）。建议随后增加Terran Armed Forces与本次4新势力双向对抗8包，合计25；这是明确的优先扩展子边界，不隐含生成全部90个有向对抗。16可区分“基础发布”和“优先对抗扩展”完成状态，不把17包覆盖说成25包完成。

无专属对抗包时，可明确使用适用的总规则＋双方势力事实＋本族策略及统一查询工具；UI与报告标“通用对抗配置”，不得暗中加载其他势力对抗包。它能保证规则能力，不保证与专属对抗策略同等水平。

### 执行步骤

1. 将13的失效章节清单变成可追踪生成作业。总规则先修真实通用变化，再修涉及的势力策略，最后修有向对抗；每阶段只传必要上下文和当前章节，保留整包结构与交叉引用。
2. 事实槽由Host从release填写：价格、Supply、能力、阶段、地图/任务、合法查询结论。模型写条件化判断、计划、比较和公开理由，不抄回执/hash/坐标身份；不要求输出隐藏思维链。
3. DSH仅用于离线Skill生产。复用既有ctx2skill/Teach、增量编辑及结构化编译入口，不另造线上DSH对战链路。具体角色可用性先按工程先行标准证明。
4. 用受影响的真实案例提出“为了哪个目标、什么场景、方案与替代各有什么收益和代价”。实验预先写出不同结果会怎样影响选择；可得出有条件保留、替换、无法判优。不能把没有证据写成劣势，也不能把无干扰到达证明扩张成实战必胜。
5. 验证事实、适用域、来源与可执行建议。审核器不因偏好另一种合理策略无限要求重写。相同条件/同证据/同方案再次提出时复用已完成比较，或明确终止该可选比较并保留未定。
6. 工程通过后做小批真实生产，按作业保存原请求/回复、工具证据、费用和当前后继。输出截断只处理未完成块；已保存且可解析回复先消费，不盲重购。
7. 将候选送独立评价窗口：旧/新Skill使用同release、军表、地图、双方能力和起点；评价应覆盖修改的生效阶段，若改部署/路线不能仅验证突击。报告骰子/采样策略，不能用单次胜负证明策略更优。
8. 事实正确且可读可用后可进入明确候选试用；“策略提升”需独立对比证据。Wave3第一次上线可以标“基本可用、效果待评”，不靠无限Teach把发行永久卡住。

验收分开登记：新增/更新包完整性；正式注册器及用户/机器人读取成功；真实产出；独立策略效果。缺任何一层不能借其他层顶替。统计Token与费用，未返回请求的费用为未知，不记0。当前暂停不能因文档中的步骤自动解除。

交付：增量差异可读版、包/章节适用域、生成和消费回执、比较报告。相关新经验可进入后续WikiSkill/SkillOpt/Memento-VISTA，但不恢复本轮暂停的研究。

## T28-W3-15：Web/App统一产品使用路径

依赖03、06～12；13的版本选择可先接工程候选。不要把手工实验脚本当作最终入口。

现有入口：packages/http-adapter/handler-v1.mjs，packages/client-domain/native-action-form-v1.mjs、battle-workbench-v1.mjs及相关threat/probability/viewer模块；apps/starcraft-tmg-battle-lab与apps/starcraft-tmg-expo。使用既有API前缀/starcraft-tmg-level3/api/v1；如必须扩接口，先定义合同/旧客户端行为，不虚构已经存在的endpoint。

步骤：

1. 数据库页可按release/势力查看新单位、模式、武器、卡/升级、原文和规则说明；资源缺失显示清楚的文字fallback，不让空头像代表单位消失。
2. 写表器列出合法选择、预算与剩余资源、明确的非法原因。人工写表、AI从头写表、固定表写Plan都能保存并作为同一房间配置输入；双方可见信息按模式隔离。
3. 创建房间时选择规模、地图、任务、部署、release和操作者类型；保存后所有面板读同一Room投影。旧房能回看旧规则，新房不能混版本。
4. 新主动、反应、被动触发结果进入对应面板。目标、模式、摆放、替换、卡片和资源支付通过合法菜单选择；回合/阶段变化后旧菜单失效并刷新，不能执行上一revision的动作。
5. 地形轮廓、底座、token、血量/分伤、增援、控制点和威胁开关共同验收。范围裁剪到棋盘，单单位/多单位叠加可开关；显示是规则结果投影，不能由前端再算一份独立距离。
6. 副官浮窗保留头像、多角色、中文、放大和历史读取；它读取所在席位允许的事实、Plan和公开观察，不因新规则绕过视角隐藏。建议不能直接写权威状态。
7. BYOK按当前用户/席位绑定：人人的各自副官用各自配置，人机的机器和该用户助手用用户所选配置。保存方式沿既有安全实现，报告和截图不含密钥；不能把开发者Key打包给最终用户。
8. 人机合法动作按房间策略自动执行并告知；需要玩家选择移除自己的模型等交互时有明确待办和可委托选择。人人两席各自权限；机机同样使用机器方产品入口，不多一套实验专用Apply。
9. 回合setup/teardown、增援、计分、结束/胜负提示，用实际工厂构造隔离边界状态快速验证。可以mock状态起点，不能mock被验收的规则或假造通过回执；不必为了测试一个终局面板打满五回合。

10. 以冻结的新增／变更单位 ID 对照各端单位图标、通讯头像、语音事件与棋盘标记；新增单位或模式逐项核对来源与实际加载。BGM 作为战桌功能实测选曲、播放、暂停、循环和音量。采用[跨版本媒体准出表](project-continuation-roadmap-2026-11-22.zh-CN.md)，缺件不会计为已覆盖。

验收：桌面Web＋窄屏的真实UI操作截图/回执，人工军表创建、AI任务入口、至少一个新能力、反应/目标选择、跨回合、胜负、刷新/断线重连。App共享domain工程验证单列；无安卓设备不宣称APK真机验收完成。使用现有浏览器能力/已授权Playwright，不擅自安装。

交付：用户操作说明、具名截图索引、操作→API→Room回执对应表、未完成设备边界。没有真实Token时AI入口可以工程注入验证，最终真实产出仍留给16。

## T28-W3-16：三模式准出、可回滚发布与最终报告

依赖12、13、15，真实AI部分依赖14的基础包及调用恢复。最终发布只收本次明确范围，不把18张后续地图或全部90方向Skill塞进来。

分两层做，避免“跑一整局等于所有规则都验证”：

- 规则接线层：414产品定义均有归属；新增162和旧实质变化逐项有绑定/复用/退役说明。每个受影响唯一行为走产品正向与拒绝边界；反应、被动、延迟、生命周期必须有实际触发证据。不能用未执行的登记行充数。
- 用户产品层：人人、人与AI、AI与AI完成下面的操作矩阵；军表、Map、任务、rulesRelease和Skill来源一致。所有公开提供的游戏规模有创建/部署/计分边界验证，实战主验2000分Standard；Skirmish先验证现有500分工厂及其他正式支持规模，别凭空把任意分值宣称官方模式。

| 场景 | 必验结果 |
|---|---|
| 人人 | 两席创建/加入、合法军表、交替操作、反应/分伤、越权拒绝、回合setup/teardown、胜负与恢复 |
| 人机 | Web创建、用户BYOK、机器查询/决策/执行同服务、等待用户单位选择/可委托、合法错误刷新、断连恢复 |
| 机机 | 两席共享正式AI入口、持续推进、记忆与Plan后继、自动反应/阶段、计分终局与导出 |
| 老房 | 原release/旧数据/Skill不变，可读回放及按其既定支持恢复；缺原依赖明确隔离 |
| 新旧混用 | 不能在同房把新版候选/缓存应用到旧state，错误不污染任一原房 |
| 发布回滚 | 默认新房指针回旧release；已创建新房保持新绑定，不批量降级 |

工程收口后，真实实验按最小有效集合执行：一场2000分人机完整产品流程、一场2000分机机完整流程；人人用真实两席和可快速跨回合的隔离状态验收。额外种族/新机制用具名场景覆盖，不能依赖这两局恰好触发全部能力。用户若安排其他实验矩阵，以其最新指令为准；本手册不启动付费任务。

性能记录分开：恢复启动、查询计算、模型等待、动作Apply、UI/导出。用已有受影响类型快/中/长样本比较同输入、同输出语义，记录并发场景CPU争用和尾延迟；不把读入历史恢复计为每次玩家行动。不能牺牲策略信息/合法性来凑固定秒数。显著劣化先找重复计算、缓存版本、串行独立查询；无法无损解决时给出具体代价供用户决策。

交付：发布候选、来源/原子/工具/消费者覆盖矩阵、三模式证据和用户报告；已知问题按严重度/范围列出；回滚指针与恢复步骤；后续18图、专属对抗扩展等独立待办。实施完成不等于策略效果已提升；最后汇报四层状态。

发布条件：范围内Critical/High事实或工程错误为0；缺失行为不得隐藏为软成功；Medium可记录随发布。最终切默认版本/Git提交按当时授权执行，不覆盖旧对局和研究。
