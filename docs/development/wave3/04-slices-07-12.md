# 04 — 子项07～12：新增能力纵切、任务与工具

共同依赖：01来源、02发布、03编军、05相关FAQ、06几何。新162效果定义已经逐条列入实施清单，不能只按英雄举例验收。原子归属与产品路径使用02规范。

## 每族共用的施工顺序

正式房接线按发布差分推进。沿用旧房已验收的执行器与规则原子。稳定能力身份、行为一致性、宿主和运行时前置均核对后，继承旧执行路径。新增、含义变化或运行依赖变化的定义才修改对应组件。验收只补本次受影响的产品交接、至少一个实际消费后继，以及必要的旧版回执兼容检查。组件覆盖与正式房完整准入分别登记。

| 发布差分 | 接线路径 | 本次验证 |
|---|---|---|
| 行为和依赖一致 | 稳定ID指向原有执行器，引用已通过的产品证据 | 仅核对新发布确实绑定同一执行器 |
| 只改价格、数值或展示 | 更新对应的发布资料，沿用同规则消费者 | 只验受影响入口的读值与结果 |
| 新组合、规则变化、依赖变化 | 组合现有原子，补足缺失行为及接线 | 验证实际受影响的菜单、结算、后继和恢复 |

Marine 在 U71→U83 写表器差分中仅改小队 160→170 矿、大队 210→220 矿，Stimpack、Combat Shield 和 C-14 原有执行逻辑沿用。候选版已有[主动能力复用证据](../../../build/ticket-28-protoss-wave3-20261120-v1/formal-match-admission/release-active-ability-reuse.json)及[C-14 射击复用证据](../../../build/ticket-28-protoss-wave3-20261120-v1/formal-match-admission/release-intrinsic-weapon-effect-reuse.json)。个别能力的复用证据适用于所验证的动作，完整开房另看正式 Match 的发布覆盖和依赖。

当前 Standard／Skirmish 验收军表没有 Siege Tank 或 BT 武器。Standard 优先复用已购 Slugthrower、Grenades - Frag 的 C-14 被动消费者。Shock Cannon 与 Siege Mode 在含坦克军表的独立范围增量接入，复用已有签名回执和冷恢复；只验证新发布绑定与受影响的后继。 [开房军表](../../../build/ticket-28-protoss-wave3-20261120-v1/formal-match-admission/disclosure-and-legal-rosters.json) [原 Tank 模式回执](../../../build/ticket-28-wave2-capabilities-20261113-v1/tank-mode/REPORT.zh-CN.md) [原 Tank 武器冷恢复](../../../build/ticket-28-wave2-capabilities-20261113-v1/tank-weapon-ir/cold-recovery.json)

先按已定事实为每定义选择现有family／原子，再补缺少的确定性操作。每完成一个最小能力组合，即接菜单、被动/反应/阶段事件、实际Room、查询、持久化、UI。共用定义复用组合证明，但每个产品绑定必须核参数、资格、注册键和消费者；不需要让LLM逐条“证明”规则正确。

能力状态至少区分资料已导入、原子已复用/实现、runtime已注册、产品已触达、查询/执行一致、恢复已过。数量不能互相替代。

## T28-W3-07：Wave 2补齐

对象：Siege Tank、Ravager、Immortal、Zeratul、Nerazim Watchers；Cocoon、Factory (Tech Lab)、Nerazim、Robotics Facility、Void Seeker。合计55定义；准确每条见inventory。

步骤：

1. 分类武器／主动／被动／反应／生命周期；对8类effect family定位已有实现，记录需要新组合而不是新增同义原子。
2. 首先关闭模板/范围和变形等多个后续W3对象会复用的能力；购买资料与战场状态转换分开。
3. 接每单位完整合法动作/自动修正，以及新卡提供资源、资格和效果。工具看到装备、模式、实际生效距离和阶段条件。
4. 实际Room分别执行最小必要动作链；窗口后继和结束清理要经过正式match runtime。更新client-native表单可选字段。

关注组合：Tank的模式/射击与范围，Ravager的延后效果，Immortal的防御和目标条件，Zeratul/Nerazim的隐蔽/位移/反应，Cocoon等变形或生成流程。具体数值均读冻结原文，不用RTS游戏印象代替桌游规则。

准出：55定义有明确用途和绑定，所有新增可执行组合有产品后继证明；相关概率/路线与Apply一致。旧阵容与新对象可以同场，不串资源/所有者/几何版本。

## T28-W3-08：Terran Wave 3

对象：Raven、Nova双模式、Spec Ops Marauder、Auto-Turret、Holo Decoy、Sabotage Drone；Nova Covert Ops、Vanadium Plating。以inventory条数为分母。

步骤：

1. 新单位及模式对应的军表选择、唯一性、卡资源和阵营绑定接到03；明确不同资料/模式是不是同实体，依据正式卡判断，不能默认两只独立英雄。
2. 生成物使用共有实体生命周期：创建者、所属方、配置继承、控制资格、次数、到期；不要把所有对象统一塞成无规则marker。
3. Raven飞行、攻击、防护/标记、延迟触发逐项绑定。来源消失后的延时效果按FAQ保存必要快照和触发规则，不因没有actor对象直接丢事件。
4. Nova相关目标、诱饵、替换／反应使用已有窗口协议；主人和受益者不能靠显示名称匹配。
5. 把新对象及效果加入威胁/损失查询与UI，必要选择由玩家/Agent提供。

准出：基础无升级与一个受影响升级组合；生成→查询→实际触发→到期；来源移除后相关延迟分支；合法/非法目标；关闭恢复重复提交不产生两个对象或两次伤害。Raven炮台范例详02，不能以它代表全部定义。

## T28-W3-09：Zerg Wave 3

对象：Defiler、Zagara、Bile Launcher、Vileling；Defiler Mound、Reactive Creep、Zagara’s Swarm。

步骤：

1. 把牺牲／资源转换、creep来源、范围状态和伤害等拆成已有事实操作；所有模型移除都进入统一损失与当前Supply处理；按来源标明击杀、牺牲、到期等原因，再由任务规则决定是否计分，不能把自我牺牲自动算敌方击杀。
2. 新creep形式、可移动token和特殊部署渠道注册实际几何与时机。一次性计数属于真实规则实体，不附在临时prompt。
3. 延迟区域效果保存触发边界、范围、友敌影响与来源条件；查询返回预测适用条件，实际结算读取那个时间点的权威状态。
4. 大小编制/衍生单位的当前Supply用正式squad profile与上下文查询；不从small/large标签猜人数或占点能力。
5. 对现有creep/omega等共用消费者做影响对账，仅重新验证本次改变的边界。

准出：一个合法支付/牺牲、拒绝错误对象/资源；损失同步Supply和任务；creep生效/失效；区域效果跨边界和到期；同一事件多次读取消费不重复。费用、当前人口、控制人口、损失分在报告中分别列出。

## T28-W3-10：Protoss Wave 3

对象：High Templar、Tassadar、Twilight Templar；Templar Archives、Templar Caste。

步骤：

1. 力墙等对象有独立规则类型、几何与期限；与旧Sentry Force Field是否共用规则按原文决定，不能因名字相似直接套用。
2. 范围伤害/屏障/费用修正统一写入对应kernel；多个范围重叠是否累计按原文，不能每个token循环扣一次就默认正确。
3. 把额外连续激活、授权他单位行动、当前激活者继续可用能力区分为状态机事件。保存父激活、受益者、已经消耗的行动及后继，不能只改activated布尔值。
4. 依照同一payment contract消费和刷新资源卡；角色判断不参与实际CP/PE计算。
5. 玩家和Agent都可选择受益者、目标、墙位置等；查询明确当前一步可用与将来条件。

准出：墙的两类Size通行及相关移除、范围覆盖重叠、受益者/激活者权限、连续激活的前后交替、费用折扣一次与到期、冷恢复回到正确父动作。给出完整阶段局部操作图，不用只显示一堵墙的截图代表完成。

## T28-W3-11：新任务和部署

对象：Artefact Hunt与Fire in the Sky的Standard/Skirmish四记录、三个部署记录、Gather Skirmish阈值等真实旧差分。复用已有任务原子和FAQ已有语义，不把“数据库新记录”视作所有任务逻辑从零。

步骤：

1. 新任务生成来源化参数/状态初值/允许动作/时序，映射到 official-mission-runtime-v2 与 current-product-match-runtime；新部署生成本规模的区域、进场边和目标坐标。
2. 搬运、掉落、交付、等级变化等均走权威动作与事件；每个变化标谁有权、在哪阶段、会不会消耗行动。
3. mission_marker_control读取实际资格、双方竞争者和状态，任务得分准备读取同结论；计划的“条件预计分”和实际award分开。
4. 新任务/部署可在产品setup中选择；将实际配置传到Builder读图、Plan、房间与副官。名称相同不能代替实际参数一致。
5. 处理阶段/回合交替、人口增长、第一回合特殊条件和终局吸收；旧任务以原release保留。

准出：每种任务×规模都有场景证据；setup、特殊动作、失败资格、跨回合、计分/终局与冷恢复。数据驱动场景可合并一个验收入口，不能只测Standard并宣称Skirmish通过。使用隔离产品状态跳到检查边界，标注局部工程场景，不伪造整局历史。

## T28-W3-12：统一工具和全部调用入口

依赖07～11。能力纵切已经接了工具，本项收口consumer矩阵和遗留缺口。

强制核对的入口：

| 入口 | 原有落点 | 最终应观察什么 |
|---|---|---|
| 人工Builder | army-builder-query-port-v1 + 产品服务 | 新价格、合法候选、保存军表 |
| AI从头写表 | roster-planning-product-module-v1 → roster-decision-product-journey-v1 | 模型选语义，Host绑定；表/Plan同版；工具事实回交 |
| 固定表Plan | preset-roster-journey-v1及同产品工厂 | 军表不变，地图/对手/新规则确实到作者 |
| 在线Planner/Action | room-backed adapter、spatial-action-query-runtime、live-flash-decision-port | 读到新合法能力、概率和位置；实际选择候选可执行 |
| 异步worker | readonly-query-worker[-batch]-v1 | 同发布、同条件；过期结果不作当前事实 |
| 编辑/纠错/保存答恢复 | 原workflow/run/journey外层 | 更新合同被所有入口消费，保存语义不丢 |
| UI工作台 | client-domain下native-action-form、threat/probability/workbench | 同菜单、同字段语义，未求值明确显示 |
| 副官/复盘 | 按本房读上下文的实际产品端口 | 当前发布、权限范围、历史/假设/实际分别标记 |

实施步骤：逐行登记producer/consumer函数→实际字段→具名场景→保存结果；查询端不能独立硬编码数值。每个首次、编辑、错误回交和保存回复恢复的真实可达分支都需有对应证据；共享代码可复用一份，不做四套相同测试。

准出示例：同一新单位在新release，Builder审计、Plan场景查询、live query与RoomApply使用同数据；一次查询worker期间revision变化被拒为过期而不改房间；一次有效保存回复无需重新付费被外层消费并推进。不能用手动调用完成helper或只有入队状态代替后继已收到结果。

Tool能力不足应只补这个具名能力，不让模型发散查整场结果。有限摆放miss交回模型选择（改意图、查别处或选别动作），保留有效已查证事实；工程不强制pass，不把miss声明为规则非法。
