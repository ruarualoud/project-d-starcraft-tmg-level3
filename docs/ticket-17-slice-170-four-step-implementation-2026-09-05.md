## 为什么这次不再整轮回炉

生产实现集中在 packages/skill-production/，不是每次 API 失败新增一份 Broker 版本。
阶段输入、已读来源、正常输出、引用、审查、修订和用量都有可恢复记录。
每个 arm/章节/角色/修订独立命名；已完成上游不因下游失败被丢弃。
跨代码修复不是静默兼容：continuation 明确绑定父 recipe、允许变化的工作流文件与新旧 hash。
来源、引用/语义门、内核、模型、工具或限额改变则拒绝继承；只复用输入 hash 完全相同且有完整正文的角色节点。
已完成章节不直接搬成“通过”，而是重建引用/审查/内核比较；继承回执逐节点保留父产物 hash。
父调用的 token、费用、次数以及开始时间从续跑预算扣除；不复制调用记录为新消费，也不重置上限。
同一调用的请求 hash 不一致拒绝复用；请求可能已经发出而没有可靠结果时保留预留费用并停止。
数据库事务不横跨网络等待；过期 lease 通过 generation fence 拒绝迟到写回。

原始 Provider payload、reasoning、凭据均不进生产账本；只保存经过既有隔离端口检查的结构化输出和安全 usage 元数据。
坏 JSON、空正文、finish_reason=length 即使带完整 JSON，也先记录可信 usage 再拒绝/局部修复。
实际校准发现模型会漏掉最外层对象的最后一个右花括号。新增严格、确定性的词法检查：
只有字符串都闭合、内部括号完全匹配、栈只剩最外层对象、补一个右花括号即可被标准 JSON.parse 解析时才接受。
原字符串是修复结果逐字节不变的前缀，回执标记 outer_object_close；不修引号、逗号、字段、值或缺失成员。
完整单个 JSON 围栏可以剥除；有其他说明文字则拒绝。finish_reason=length 仍拒绝，不因能补括号而接受截断响应。
缺 usage 不伪装成零；未知模型保留预算并停机，不自动切模型。

## 证据与评价不混为一谈

实际章节试产进一步暴露出“让模型逐字抄引文”的脆弱性：表格/段落换行被模型折叠后，含义可能没变，但精确引文门会反复拒绝。
当前 wire 因此明确改为 host_materialized_source_spans_v1：模型只返回 ref + spanId，宿主从冻结正文按固定段落边界还原引文、偏移和 hash。
所有可读来源的 spans 重新拼接必须逐字等于原文；编造编号拒绝，不进行近似引文匹配。
语义 verdict 统一为 supported / unsupported / unknown，只有 supported 可通过。改变否定标签名称不改变拒绝标准。
旧 quote-wire 的未完成 recipe 和产物保留隔离，不能被新 recipe 静默读取为已通过。
独立审查者仍须判断“该段落是否真正支持这句话”，选中合法段落并不自动通过语义门。

引用检查只证明引文在冻结原文里。每条渲染文本仍须语义审查，策略只能作为有条件的推断。
正向审查与对抗审查分别从新上下文开始，彼此不见对方回答；分歧才进入第三个仲裁上下文。
模型共识不授予 Rules authority，也不代表策略已被对局证实。
正式试产先跑正反校准：同一真实 FAQ 引文，一条正确陈述、一条反向假规则，分别检查是否接受/拦截。

Mechanics Verifier 真正调用当前冻结 FAQ 内核，预期值由测试夹具固定，不能由待测内核现场生成预期。
开发集 36、留出集 36，输入不重复；留出探针不开放给生成工具。
独立 Student 在未见预期答案时给出预测，再与真实内核执行比较。
第一轮另暴露题目歧义：例如 cardNameBlockIgnored 是诊断标志，legal 在某些查询里只是“查询可执行”，并非技能描述的完整动作合法性。
原始接口字段评分保留不改；补充评估对同一冻结候选改问明确的规则结果，不向模型提供预期答案、不重新生成候选。
补充题是事后澄清，不包装成预注册盲测，也不能用于宣称 DSH 显著优于 direct。
错误答案原样留档；只允许一次输出结构修复，不能将得分低作为重答到正确的理由。
序列化机制执行日志可在新的 verifier 实例重新执行并比对输入、来源、依赖和结果；依赖不匹配隔离。
这是机制级回放，不是完整房间日志回放，更不是整局胜率实验。Room/arena 对局效果仍属于后续 Ticket18/20。
