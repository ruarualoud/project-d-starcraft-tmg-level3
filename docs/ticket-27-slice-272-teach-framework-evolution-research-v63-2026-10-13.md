## 1. 要解决的是两层进化

用户的 Marine、Goliath、Raynor、轻甲／装甲需求等，是**思考维度的例子**，不是必须选择的单位或必答场景。
模型先学习该战棋游戏的策略问题结构，再从本局任务、地图、双方公开军表与已有 Skill 中识别重要矛盾、提出可证伪假设和取舍。
复盘不只修改玩法，也必须审视产生这些质疑的 Teach 方法是否有效。

- **策略 Skill**：怎么写表、部署、获胜、反制和调整计划。
- **Teach 框架 Skill**：该问什么、为什么问、怎样选择场景／工具、什么证据足以支持或推翻一种方案、何时保留合理风险。
- **不可由两者修改的权威层**：官方冻结数据、Rules、合法性、真实计分、工具语义、晋级评估器和实验分组定义。

这里的“学习”首先指受控工具学习、Teach 和离线 Skill 编译，不承诺训练模型权重。

## 3. 一手资料与取舍

以下只提供方法，不作为 StarCraft TMG 规则或已证明的项目效果：

1. [美陆军 How to Master Wargaming](https://api.army.mil/e2/c/downloads/2023/01/31/bf65892d/20-06-how-to-master-wargaming-public.pdf)采用行动、对手反应、己方再反制的推演。适合把单边计划改成可检查的交互假设，但本项目仍由 TMG Rules 裁决。
2. [CICERO 官方介绍](https://ai.meta.com/blog/cicero-ai-negotiates-persuades-and-cooperates-with-people/)把局面、历史、对手预测与策略计划结合；说明语言表达不应替代策略判断。其 Diplomacy 成果不能直接推断本项目的战棋效果。
3. [AlphaStar 官方介绍](https://deepmind.google/blog/alphastar-grandmaster-level-in-starcraft-ii-using-multi-agent-reinforcement-learning/)使用能暴露策略弱点的训练对手并保留策略多样性。借鉴“寻找反例而非强迫保守”，不复制其训练资源或电子游戏规则。
4. [WikiSkill 原文](https://arxiv.org/html/2608.27454v1)区分原始经验、累积知识和可执行 Skill，候选通过验证后才保留，拒绝记录继续沉淀。适合分别积累“玩法经验”和“Teach 方法经验”；其基准收益不是本项目效果证据。
5. [EvoTest 原文](https://arxiv.org/html/2510.13220v1)在 episode 间演化提示、记忆和工具使用方式。适合把 Teach 方法纳入可演化对象；本项目先限制为框架正文和取证程序，不授权生成任意代码或改权威规则。用户给的 ICLR 页面本轮读取失败，结论来自论文，不声称已核对会议页面。
6. [Reflexion 原文](https://arxiv.org/abs/2303.11366)用执行反馈与经验记忆支持后续修正。借鉴反馈留存，不把自我反思当成事实判断或策略提升证明。

下面的框架、合同和验收设计是**本项目的设计推论**，不是上述论文已提供的 TMG 成品。

## 4. 初始框架：覆盖维度，而不是固定答案

先给模型一个中立的覆盖骨架。模型读取冻结的 TMG 原文、执行工具合同、接受的总规则／本族／有向对抗 Skill 后，编译成游戏专用框架；每次写表再实例化本局问题树。
人手写的骨架不能标成“模型学会了”；需要保留真实读取、提出问题、查询与修订的记录。

| 维度 | Teach 应质疑什么 | 需要的证据／定量内容 |
| --- | --- | --- |
| 获胜路径与需求 | 在何轮、以何种方式达成胜利？占点、击杀、拒止怎样相互支撑？对手不配合时还能兑现吗？ | 任务时序、合法控制判定、分数窗口、到达安排；模型提出自己的需求，不套统一权重。 |
| 对手与场景 | 对方哪些实际单位、能力、组合会阻止路线？最可能与最危险但合理的回应是什么？ | 公开军表、完整武器／能力／升级、可见资源；未知的选择或未来位置是明确假设。 |
| 军表机会成本 | 为什么用这组单位／规模／升级而不用其他合法组合？节省资源如何重新分配？ | Builder 合法组合与真实总价，单位、升级、战术卡和到达代价；允许回到选表，不把临时快照当作选择理由。 |
| 交互与能力需求 | 在明确目标和位置下，需要多少反轻甲／反装甲能力？哪种组合能更好地满足这个缺口？ | 同条件 Rules 概率查询、射程／LOS／参与模型、主动能力／卡牌条件。属性标签只是机制输入，不是战略排名。 |
| 伤亡后的剩余能力 | 损失谁以后会失去火力、移动／连续性、配合、Supply／控制能力？英雄真的更耐损吗？ | 实际损失模型／单位分布、剩余模型与伤值、Supply 档位、几何依赖。必须比较完整分布／尾部风险，不能仅报平均伤害。 |
| 位置、地形与队形 | 计划所需道路、可部署区、火力圈、遮挡、占点位置能成立吗？编队／屏障／侧翼怎样改变交互？ | 同地图规则几何、底盘、全路径与控制查询。部署边距不等于攻击距离；格网可达不等于一个动作可达。 |
| 时序、协同与反制 | 支援与伤害能力何时可用？移动／射击／近战／Run／Pass、增援先后如何服务长期目标？对手插入激活后怎么办？ | 真实阶段、可执行动作、资源和触发条件；行动→回应→再反制的命名分支，不用“随便执行首个合法动作”代替预测。 |
| 鲁棒性与改计划 | 哪些假设最敏感？什么新信息足以换单位、改路线或坚持风险？ | 场景扰动、替代方案的收益／代价差、可观察触发条件和查询成本；不确定不自动等于撤退。 |

模型给出本局适用／不适用／待证的维度及公开理由，然后优先查询**可能改变选择**的假设。
每批只问当前关键问题，保存未覆盖分母并可继续；不要求每单位每批穷举同一套问题，也不能把少数成功问题称为全覆盖。
保留问题生成器的自由，不强制必须有 Marine／Goliath／Raynor，也不硬编码这些单位的优劣。

## 5. 定量查询的正确位置

比较必须先说清场景：双方组合／升级、规模和损失、时点／阶段、位置／地形、先后手、能力与卡牌、对方响应假设。
同一场景下，工具比较合法备选方案；模型解释差值是否重要及为什么接受代价。

- 优先复用现有 `pregame-scene-laboratory-v1` 的 `queryProbability`、`queryThreatExchange`、`queryScene` 和只读假设分支，它们使用实战同一套 Rules／场景查询。
- 当前 `queryProbability` 只支持当前合法远程攻击域，不可拿其 `unknown` 猜出冲锋或近战胜率。缺少场景／动作域时先补合法的命名假设和取证；仍不支持的工具能力明确记录，不能手写另一个公式凑数字。
- 分开报告期望、样本／精度、可能损失状态、对方反打和占点后果。未知是未知，不是零；条件性优势不是普遍优势。
- “需求多少”由模型从胜利路线推导假设，再查询它是否满足；Host 不给自创的伤害／生存／占点加权总分。
- 能确定性计算的供给和预算由源数据／Builder 计算；损失后状态由 Rules 结果推导，不凭模糊 small／large 标签下结论。

## 6. 把 Teach 框架纳入原有自进化闭环

```text
写表／Teach 公开记录 + 实战结果 + 场景实验
                 ↓ 关联同一假设与 Plan 血缘
玩法知识 Wiki                 Teach 方法知识 Wiki
     ↓                              ↓
策略 Skill 候选                Teach Skill 候选
     ↓ 实战同状态对照                ↓ 同预游戏输入重跑 Teach／写表
冻结留出与对手回应 → 晋级或回滚；失败经验继续保留
```

两条 Wiki 是独立知识命名空间，不必另造两套存储。运行中的玩家和教师读取已选定的 Skill，不读取含未来结果／留出答案的研究 Wiki。
一个 Skill 更新只改变一个目标；先区分“玩法改好了”和“教法改好了”，再考虑两者组合。

### 6.1 必须保存的公开记录

`frameworkSkillRef/version`、来源／规则／工具合同版本、军表／地图／任务、初始小计划；
每条问题的父维度、针对假设、提出理由、证伪条件、替代方案、查询及回执、假设与精度；
学生的 retain／revise／unresolved、前后军表／Plan 差异和改动依据；
后续真实执行、预测校准、对方反应、工程失效、实验结果和晋级／回滚。

只存公开决策解释与实际工具交互；不要求提供或落库隐藏思维链。仅留摘要而删除唯一取证回执，会使框架改进不可验证。
脏工程轨迹可作为工程／Teach 失效诊断，不作为可靠策略胜负、MuZero 真值或有效策略晋级样本。

### 6.2 框架本身的复盘点

- **漏问**：实际失败的关键条件是否已有足够信息却没有质疑？若当时不可知，要评估条件计划，不用事后事实责怪模型。
- **误问／误否定**：教师是否基于错误工具、规则或无依据风险，把有证据的主动打法改差了？
- **取证无效**：是否用了不回答该问题的工具、重复查询或把 unknown 包装成比较？
- **修订作用**：问题是否让模型改变了可观察的军表、Plan 或条件分支？坚持原方案是否有有效依据？
- **能力损失遗漏**：只算伤害，是否漏了模型移除造成的机动、火力、Supply、协同和任务收益改变？
- **泛化与成本**：换对手／地图／位置／规模后仍有用吗？冗余 Teach 的时间和 token 是否值得？

这些是评价维度，不是硬编码战略奖励，更不是教师必须让学生换表的指标。

### 6.3 晋级需要不同的实验 Adapter

现有 Room checkpoint 对照用于策略动作，不应直接用于 Teach 框架。新增 `pregame_teach` 实验 seam：
冻结同一预游戏输入、小计划、技能、工具、角色模型／配置和可用预算，只替换 Teach 框架；各 arm 保存独立真实记录与费用。
从头写表时允许候选军表和 Plan 发生变化；成表写计划时军表保持相同，不混淆两类任务。
再用同一实战链路、冻结对手与可比 RNG 做下游实验。预游戏过程指标与最终对局指标分别报告，LLM 输出不可保证逐字确定性。

晋级要求：权威事实／合法性无新增 Critical/High，关键问题的检出／误否定和策略兑现有实证改善，合理冒险与策略多样性未被压扁；时间／token 单独报告。
不能让候选框架重写评估器、晋级阈值或留出集。未知／低信号保留候选而非宣布有效；结果不好可回滚版本，Wiki 保留拒绝原因。
遵守三轮收敛与只验受影响部分的现有要求，不新增无限递归“审查审查器”。
