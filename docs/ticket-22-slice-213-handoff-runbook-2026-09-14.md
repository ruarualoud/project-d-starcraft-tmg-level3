## Local product operation

From `starcraft-tmg-level3/`:

```sh
npm run dev:ticket-20-human-agent-web
```

The process prints:

- `url`: the product link containing the one-time human-seat recovery material;
- `diagnosticUrl`: Battle Lab, for referee/Agent observability only.

Open the product URL, not the diagnostic URL, for normal use. The five main tabs
are Database, Army, Calculators, Battle and Settings. In Battle:

1. bind/recover the provided bounded room;
2. inspect map, models, unit/card data and chosen upgrades;
3. choose threat modes or combined friendly/enemy threat projections;
4. choose a LegalSpace action and parameters;
5. Preview, inspect the authoritative result, explicitly confirm and Apply;
6. inspect the receipt and Replay match;
7. open the bottom-right Kerrigan dock for public-fact and inferred-intent help;
8. use the postgame panel to merge reviewed episodes or preview Skill freshness.

The Database/Army/calculator data is a frozen official product projection. It
does not become room authority. Saved army drafts are product data, not a proof
that every such roster can run through the current bounded complete-match demo.

## BYOK and Provider operations

- Never paste an API key into source, logs, room state, a Skill, a report or a
  delivery manifest.
- Use the platform secret UI for session-memory BYOK, or on the current macOS
  development host run `npm run setup:ticket-17-deepseek-keychain` and enter the
  value only at the hidden Keychain prompt.
- Parent/room processes receive no plaintext key. The isolated credential and
  egress worker attaches it only to an allowlisted HTTPS Provider request.
- Model aliases and fallbacks are versioned Provider profiles. A fallback does
  not rewrite an already-settled attempt.
- A fresh generation run resets its max-call anomaly window; cumulative token
  and cost accounting is retained. Each crossed ¥100 threshold emits an
  `alert_continue` notice, not a hidden stop.
- Unknown delivery after timeout is not automatically retried. An operator must
  inspect the durable attempt outcome and authorize continuation.

## Skill generation, runtime use and freshness

The accepted foundational pack lives at
`content/strategy-skills/ticket-18-foundational-v1/`. It includes the general
rules-and-strategy Skill, faction Skills and directional matchup Skills.

Offline production order is:

```text
source/rules evidence
 -> curriculum + Teach/Ctx2Skill
 -> typed structured generation (DSH or control arm)
 -> local field/source repair and bounded recovery
 -> fact/source/consumer/strategy evaluation
 -> immutable candidate
 -> independent promotion and release
```

Online play retrieves exact accepted general + faction + directional matchup
references. It never loads an arbitrary candidate or invokes DSH. If source,
rules or a dependency changes, the freshness runtime traverses reverse
dependencies, classifies only affected Skills as stale and produces a review
plan. Unaffected Skills remain accepted.

Postgame work is manually triggered, may merge several exact episodes, may run
bounded asynchronous counterfactual branches from a frozen state, and produces
SkillOpt candidates. It does not edit the original room or accepted Skill.

## Incident handling

1. Classify the finding. Medium is recorded and monitored; Critical/High
   quarantines only the exact environment/release/subsystem scope.
2. Preserve source versions, room journals, release identity and low-cardinality
   telemetry. Never copy prompts, secrets or private state into an incident note.
3. Stop new work in the affected scope; do not mutate completed historical jobs.
4. An administrator may activate only the release's declared predecessor.
5. Verify recovery under a distinct principal; then resolve the exact incident
   scope without reopening unrelated quarantines.
6. Rules/source/Skill/training truths remain unchanged unless their own review
   authority issues a new versioned decision.
