## 已修复的问题

1. 引用不再靠模型抄写。模型选来源及段落编号，宿主还原冻结原文、偏移与 hash；伪造编号被拒绝。每句规则、策略和注意事项都进入清单，两位独立审查者判断真实支持关系，分歧由第三个上下文处理。
2. 用量在解析正文之前落账。只允许确定性的外层括号/单一 JSON 围栏修复；格式修复和语义修订有次数上限。模糊发送不自动重试，未知消费不记为零，余额耗尽停止其他开发。
3. DSH 真实选择 read/query/probe 并收到工具结果，再决定下一步。Direct 保留对照；没有把宿主安排的固定动作伪装成模型自主工具使用。
4. 成功角色节点有完整正文与输入 hash。工作流修复使用显式父链续跑、重新校验结果；原始费用和开始时间累加，成功上游不重复付费。

现场暴露并修复了两类宿主问题：数组超限的反馈缺少实际计数；结构修订丢失上游已经执行的来源读取记录。
修复前失败的 recipe 与账本均保留；没有通过删除失败、放宽引用/语义门或改写模型答案来完成试产。

## 怎么解读质量分数

原始留出测量直接询问内核输出字段，其中混入 `cardNameBlockIgnored`、查询结果的 `legal` 等诊断字段。
这些字段错误不能一律解释为游戏规则错误；例如能力范围判断正确，但把查询可执行的 `legal` 当作能力使用合法性，会导致整题失败。

补充测量保持候选正文不变，用另一个独立上下文询问明确的规则结果，例如：

- 仅实体卡移除限制是否阻止这张卡被选中？
- 装甲伤害与 Surge 伤害合并后，Evade 前的伤害池是多少？
- 同一件地形与给定距离是否满足直接掩护条件？
- 自身纳入范围的例外是否适用于这个对象？

原分数和补充分数并列保留。后者是事后澄清，不是预注册盲测；不做显著性、胜率或 DSH 因果收益声明。
错误答案不会被重答到正确；题目只允许一次结构修复，不提供预期答案，生成端不能调用 heldout probe。

## 覆盖与限制

- 强制来源39项：21条核心正文、18条FAQ。它们只是来源条目，不能换算成规则器或整本规则书的完成比例。
- 工程演练72个不同输入：36开发、36留出，覆盖10个FAQ机制族；每个机制实际执行内核并做确定性复算。
- 机制执行日志在新 verifier 实例回放，不等于 Room Replay，更不是人机或机机完整对局。
- 核心正文原有 review-required 状态未清除；策略建议未被实战证明；两份候选不写长期记忆、不自动发布、不进入 MuZero 真值。
- DSH 与 direct 使用相同模型、来源、工具和模型/工具次数限额，但 DSH 有独立三分钟 OS Session supervisor，direct 当前只有步数及整体 wall 上限。逐 Session wall 同构、staging效率及完整前代聚合留给 Slice171。
- 同模型的多上下文审查可能出现相关错误；一组候选与有限案例不足以估计稳定优劣。需增加来源依赖闭包、数值/边界反例、按机制分层的独立留出集，以及后续受控对局。
